## 2. 讨论中形成的建议，初步计划予以采用

- 逻辑上保留各生态，部署上可以集中；通过 Host Adapter 与 Client Adapter 降低两两兼容成本。
- 使用原生框架内核和原生语言，尽量保持插件业务源码；公共层统一可观察能力与生命周期。
- 将 MCP 能力接口、聊天事件接口、插件管理接口分开；复用现有标准，只补齐缺失的语义。
- 保留一个消息入口和一个受控输出网关，避免多个宿主分别连接同一账号并重复回复。
- 控制平面与插件执行平面分离，某个宿主失败时撤销其可用能力并独立恢复。
- 测试先建立原生基准，再与联邦运行结果比较；安装、加载、行为与稳定性分别记录。
- 自动测试环境与个人日常运行环境分开；普通子进程和依赖环境主要提供故障或依赖隔离。

## 3. 讨论前后方案的取舍

| 事项 | 早期建议 | 后期建议 | 初步计划采用 |
|---|---|---|---|
| 项目归属 | Stella 插件子系统 | 独立公共运行时，Stella 为客户端 | 独立 Ligamina |
| 首批宿主 | 先复用 Stella AstrBot 兼容层，再 Koishi，最后独立 NoneBot | 独立项目先验证 NoneBot 与 Koishi 的跨语言互操作 | NoneBot + Koishi 优先；AstrBot 随后接入 |
| 核心语言 | Python 原型 | Rust Supervisor，宿主保持原生语言；原型可先验证 | 推荐 Rust 作为交付核心，P0 通过最小实验确认后冻结 |
| 新插件标准 | 曾讨论面向联邦直接开发的新格式 | 用户随后强调复用已有生态 | 第一阶段只定义桥接契约、能力映射与测试夹具，不经营新插件市场 |
| 部署范围 | 本机子进程 | Embedded / Standalone / Distributed | 个人 Windows 优先，单机 Linux 服务验证同一契约；分布式延后 |

这些是本次规划的取舍，不表示运行效果已经得到验证。
